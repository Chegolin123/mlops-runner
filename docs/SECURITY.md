# Безопасность self-hosted runner'а

Runner — это удалённое выполнение кода на твоей машине. Относиться к нему надо как к SSH-доступу для незнакомцев, только с более узкими правами.

## Что уже сделано

- Отдельный пользователь `ghrunner`, без sudo.
- `NoNewPrivileges=true` и `PrivateTmp=true` в systemd-юните.
- Регистрация только по одноразовому токену (живёт 1 час).
- Workflow в этом репозитории не запускается на `pull_request` из форков.
- `concurrency` не даёт двум тренировкам одновременно съесть GPU.

## Правила, которые нельзя нарушать

1. **Не давать runner'у доступ к секретам больше, чем нужно job'у.** Долгоживущий токен лежит на машине; если job скомпрометирован, он тоже.
2. **Не запускать на нём код из непроверенных источников.** Публичный репозиторий + fork PR = чужой код с доступом к твоей сети.
3. **Не держать runner на машине с личными данными без изоляции.** Идеально — отдельная VM или LXC с доступом только к GPU и нужным каталогам.
4. **Ротировать registration token.** Не хранить его в репозитории или заметках; брать через `gh api` в момент установки.
5. **Следить за обновлениями runner'а.** Версия в `install-runner.sh` пиньится осознанно; обновление — переустановка с `--replace`.

## Если что-то пошло не так

```bash
# остановить и снять runner
sudo /opt/actions-runner/svc.sh stop
sudo /opt/actions-runner/svc.sh uninstall
sudo -u ghrunner /opt/actions-runner/config.sh remove --token <removal-token>

# посмотреть, что происходило
journalctl -u 'actions.runner.*' --since "-1h" --no-pager
```

Removal token: `gh api -X POST repos/OWNER/REPO/actions/runners/remove-token --jq .token`

После снятия runner'а старые job'ы, поставленные в очередь на него, не выполнятся — это ожидаемо.
