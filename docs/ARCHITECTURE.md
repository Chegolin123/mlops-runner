# Архитектура

Три части, которые живут отдельно и не мешают друг другу.

## 1. Runner

GitHub Actions не присылает задания на машину — runner сам ходит на `api.github.com` и держит long-poll. Из этого следует:

- не нужен белый IP и проброс портов;
- достаточно исходящего HTTPS;
- при падении сети job не придёт, а не потеряется.

Процесс `run.sh` живёт под systemd (`Restart=always`), работает от непривилегированного `ghrunner`. У runner'а есть label'ы `self-hosted,gpu,linux` — job без GPU на него не попадёт.

## 2. Workflow

`nightly-train.yml` живёт в этом репозитории и запускается по расписанию или вручную. Ключевое:

- `runs-on: [self-hosted, gpu, linux]` — единственная привязка к железу;
- `checkout` берёт код из `Chegolin123/mk-ai`, а не из этого репозитория;
- зависимости ставятся в venv, torch — из индекса cu124;
- лог тренировки и `metrics/run.json` уходят артефактом, сводка — в Job Summary.

Это разделение важно: репозиторий-оркестратор не знает про модель ничего, а репозиторий с моделью не знает, где он запускается.

## 3. Метрики

`collect_metrics.py` превращает человекочитаемый лог в JSON. Никакой БД: артефакт прогона — и есть запись истории. Когда понадобится график, его можно собрать из артефактов по `run_number`, не меняя пайплайн.

## Почему не облако

| | Облачный GPU-раннер | Свой runner |
|---|---|---|
| Ночь тренировок | оплата за минуты | ПК и так включён |
| CUDA | зависит от образа | своя, стабильная |
| Данные | уходят в облако | остаются дома |
| Первоначальная настройка | минуты | полчаса |

Для ночных прогонов на одной карте домашний runner дешевле и предсказуемее. Для матрицы тестов и релизов — наоборот, облако.

## Ограничения

- Один runner = один job за раз. Параллельные прогоны встанут в очередь.
- GPU-память не изолируется: две тяжёлые job одновременно положат карту. `concurrency` в workflow — обязателен.
- Runner видит домашнюю сеть. Не пускать на него код из форков и PR от внешних контрибьюторов.
